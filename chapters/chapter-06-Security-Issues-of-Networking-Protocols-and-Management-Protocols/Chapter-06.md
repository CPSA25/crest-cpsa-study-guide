**Network Management**

Network management encompasses the processes and protocols used to
configure, monitor, and maintain the integrity, confidentiality, and
availability of network devices, services, and associated data. This
critical function includes traffic generated by network management
stations and network devices themselves, utilising protocols such as
Telnet, SSH, and TFTP. The remote management of network devices presents
a critical attack surface, and security controls must be strictly
enforced. The approach to managing network infrastructure falls into two
major architectural models:

1.  **In-band Management:** Management information flows across the
    enterprise production network, typically utilising regular data
    channels, the Internet, or both. While more cost-effective for
    smaller deployments, it introduces the risk of exposing management
    traffic to the potentially less secure production network.

2.  **Out-of-band (OOB) Management:** Management information flows over
    a dedicated management network that carries no production traffic.
    OOB provides the highest level of security, fundamentally mitigating
    the risk of transmitting potentially insecure management protocols
    over the main network infrastructure.

For security professionals, network management involves restricting
device access and ensuring that secure management protocols are
consistently deployed. Examples of infrastructure components that
require secure management include firewalls, switches, hubs, bridges,
routers, and wireless access points. In the following, we discuss each
protocol individually.

**Telnet**

Telnet uses TCP port 23 and is considered a legacy, insecure protocol
that should be avoided for network management, particularly because it
does not preserve confidentiality. Telnet transmits all data, including
configuration commands and **authentication credentials (usernames and
passwords)**, in **cleartext** (unencrypted form) over the network. An
attacker performing passive network sniffing can trivially capture these
credentials and compromise the device. Telnet typically operates
**in-band**, meaning management traffic flows across the same enterprise
production network as regular data traffic. Telnet should be explicitly
disabled or blocked by default, as it represents an unauthenticated
inbound connection vector that leaks credentials.

**Cisco Reverse Telnet**

Reverse Telnet is a method for connecting to a device\'s serial console
port over a network, typically used with Terminal Servers or Console
Servers. It is called Reverse because traditionally, Telnet is used for
a client to connect to a server. Here, the router (acting as a server)
accepts your Telnet connection but immediately *reverses* the data flow
out to a physical serial line, acting as a dumb conduit between your
keyboard and the target\'s console port.​​ In standard Telnet,
administrators connect to a device\'s IP address to manage it (e.g., you
Telnet to a router to configure it). Traffic traverses the network
(Ethernet/IP). However, in Reverse Telnet, administrators Telnet to a
specific port on a Terminal Server (e.g., Cisco typically uses TCP ports
2001, 2002, 2003, and so on​), and the server redirects the session
through a Serial/Console Cable connected to the back of another device.​​
This configuration introduces a backdoor risk, as administrators often
configure Terminal Servers (such as a Cisco 2900 with an Octal cable) to
manage a rack of routers remotely. If an attackers find this Terminal
Server, they can often reverse Telnet into the console ports of other
devices in the rack, thereby bypassing their network ACLs.

**Secure Shell (SSH)**

Secure Shell Protocol (SSH) uses TCP port 22 and is the
industry-standard replacement for Telnet, providing secure command-line
access. SSH uses cryptographic technology to provide **origin
authentication** (often via public/private key pairs) and **data
integrity** (using hash algorithms). These checks ensure that messages
received were genuinely sent from the perceived source and that the data
has not been altered during transmission. The protocol relies on the
Diffie-Hellman key exchange to establish a shared secret, which is then
used to derive keys for encryption and signing throughout the session.
The SSH architecture comprises three main layers: the transport layer,
the authentication layer, and the connection layer. SSH is not just a
remote terminal application; it supports several critical file transfer
functionalities built as subsystems:

- **Secure Copy Protocol (SCP):** Provides a secure file-transfer
  service over an SSH connection and offers reliable file transfer,
  including preservation of the file\'s original date and time
  information. SCP relies explicitly on SSH for authentication and
  confidentiality.

- **Secure FTP (SFTP):** Provides a feature-rich file-transfer service
  tunnelled over an SSH connection.

- **Tunnelling:** SSH also supports tunnelling and forwarding network
  connections, enabling it to function as a Virtual Private Network
  (VPN) for secure access to resources.

While older, less secure SSH implementations existed (sometimes labelled
SSH-1. x, as suggested by references to Cisco SSH-1.99), the modern,
secure standard is **SSH Protocol Version 2.0 (SSH-2.0)**. SSH servers
disclose information about their implementation, version, and supported
protocols in a banner when a connection is established. Penetration
testers can fingerprint the server and enumerate the supported
cryptographic algorithms, key-exchange methods, and authentication
mechanisms using the disclosed information.

**Hypertext Transfer Protocol (HTTP)**

HTTP (typically TCP port 80) is an **unencrypted** application-layer
protocol used to retrieve content from a web server. When HTTP is used
for administrative Graphical User Interfaces (GUIs) or device
management, all communication, including **authentication credentials**
(usernames and passwords) and configuration commands, is transmitted in
**cleartext** (unencrypted form) over the network. An attacker
performing passive **network sniffing** can easily intercept these
cleartext packets and compromise the device\'s credentials, leading to a
system compromise. Using HTTP for management often means the management
traffic flows across the production network (**in-band**), exposing it
to potential attackers already on that network. The ability to sniff
credentials makes the device vulnerable to password attacks and trust
exploitation, where a hacker uses captured credentials to compromise the
target. In addition, many network components, including routers,
switches, and wireless access devices, ship with **default usernames and
passwords** that are easily found online. If these are not changed, the
administrative interface is vulnerable to immediate misuse.

**Hypertext Transfer Protocol Secure (HTTPS)**

HTTPS (typically TCP port 443) is the secure version of HTTP. It ensures
confidentiality and integrity by tunnelling HTTP over Secure Sockets
Layer (SSL) or, more accurately, Transport Layer Security (TLS). HTTPS
uses cryptographic protocols to encrypt data in transit, ensuring
confidentiality and integrity. This prevents credentials and
configuration data from being read if the traffic is intercepted. The
underlying TLS protocol uses cryptographic mechanisms (HMAC or
authenticated cyphers) to ensure that the data has not been modified in
transit. HTTPS provides a secure remote-access connection to network
devices and should be enforced for all GUI management interfaces.

**Remote Desktop Protocol (RDP)**

RDP uses TCP port 3389, and is the Microsoft protocol that allows users
to view and control a remote desktop. It can also be vulnerable to
brute-force password grinding attacks. While RDP is a standard tool for
remote administration, its security implementation, particularly with
respect to authentication, is critical to penetration testing. Like many
authentication mechanisms, RDP is vulnerable to brute-force password
grinding attacks. If weak passwords are used, the service becomes a
viable target for unauthorised access. Attackers use tools to attempt
numerous password combinations to gain unauthorised access. In addition,
RDP transport security settings, which determine the strength of the
cryptographic cyphers used, must be assessed. Adversaries with network
access can exploit servers that support weak cyphers to compromise data.
Although RDP services should generally be kept internal, if exposed to
the Internet, strong authentication, typically multifactor
authentication (MFA), is strongly recommended due to the high risk
associated with publicly accessible interfaces.

**Simple Network Management Protocol (SNMP)**

SNMP is primarily used for monitoring and configuration management of
network devices. It facilitates the exchange of control and status
information between network management stations and network
infrastructure devices, such as routers, switches, and servers. Its
security weaknesses vary significantly by version. SNMP agents and
managers primarily use **UDP** for communication. SNMP agents listen on
UDP port 161, and managers receive traps on 162. The protocol
facilitates three main message types. The first one is **GET**, used by
the manager to retrieve information from the agent. The second one is
**SET**, used by the manager to modify configuration variables or
trigger an action on the managed device. The last one is **a Trap,**
which is an unsolicited message sent by the agent to the manager to
notify them of a significant event.

**SNMP** **Key Components and Operation:**

- **SNMP Manager (NMS):** This is typically a dedicated host running a
  network management application (Network Management System) that
  oversees network performance and health.

- **SNMP Agent:** A software component residing on the managed device
  (e.g., a router or switch) that collects and stores local management
  information.

- **Management Information Base (MIB):** A hierarchical database
  structure that defines all device resources and activity data managed
  by the SNMP agent. Information is stored as manageable objects, each
  referenced by a unique Object Identifier (OID). For instance, the
  MIB-2 branch often allows the manager to obtain the device\'s IPv4
  routing table (ipRouteTable).

**Different Versions of SNMP**

SNMP has evolved through three versions: SNMPv1, SNMPv2c, and SNMPv3.
The critical distinction among these versions lies in their security
capabilities, or lack thereof.

**SNMPv1 and SNMPv2c: Insecure Legacy**

Both SNMPv1 and SNMPv2c operate under the same highly insecure model,
designated as noAuthNoPriv. Access control relies entirely on
**Community Strings**. These strings function similarly to passwords,
conferring either read-only access (for GET requests) or read-write
access (for SET requests). All data transmissions, including the
critical **community strings**, are sent in **cleartext** over the
network. This means an attacker performing passive network sniffing can
easily capture the credentials. Due to cleartext transmission,
SNMPv1/v2c deployments are primary targets for reconnaissance. Attackers
can trivially enumerate network information by capturing the community
string and querying the MIB hierarchy.

**SNMPv3: The Secure Standard**

SNMPv3 introduced comprehensive security features necessary for
enterprise management, designed to protect the integrity, authenticity,
and confidentiality of management traffic. SNMPv3 utilises cryptographic
hashing algorithms, such as **MD5** or **SHA**, to verify that messages
have not been altered in transit and to authenticate the message
originator. It supports **encryption** (privacy) using symmetric
algorithms such as **DES, 3DES, or AES** to secure the data payload.

**SNMPv3 Modes of Operation**

SNMPv3 supports three security levels, determined by the combination of
authentication and encryption applied:

  -----------------------------------------------------------------------------------
  Security Level     Authentication   Encryption   Resulting Protection
  ------------------ ---------------- ------------ ----------------------------------
  **noAuthNoPriv**   Username only    No           Authenticates with a username
                                                   match; provides no confidentiality
                                                   or integrity.

  **authNoPriv**     MD5 or SHA hash  No           Provides authentication and
                                                   message integrity using HMAC
                                                   algorithms.

  **authPriv**       MD5 or SHA hash  DES, 3DES,   **Highest Security.** Provides
                                      or AES       both authentication/integrity and
                                                   data privacy (encryption).
  -----------------------------------------------------------------------------------

**Trivial File Transfer Protocol (TFTP)**

TFTP uses UDP Port 69, which is a simple file transfer protocol often
used to serve configuration or firmware files to devices. TFTP requires
**no user authentication** whatsoever. Due to its lack of integrity and
authentication, TFTP is inherently insecure. If a TFTP server is
exposed, an attacker can trivially obtain configuration files (which may
contain passwords or critical network details) or overwrite firmware
images. TFTP services should be blocked by default as they are
unauthenticated and insecure.

**Network Time Protocol (NTP)**

NTP is an Application Layer protocol designed to **synchronise the date
and time settings** for devices across a network. Accurate time
synchronisation is paramount for reliable log auditing, ensuring the
correctness of security protocols that rely on timestamps and enabling
forensic analysis. NTP typically uses **UDP port 123** and is documented
in RFC 1305. An NTP system establishes a hierarchy where devices assume
a **stratum level** relative to their authoritative source. When a
system synchronises with an upstream NTP server, it assumes a stratum
level one higher than the server it references. The system at the
highest level of the hierarchy can reference a trusted NTP source (such
as a public Internet clock or a private atomic clock) or its own
internal, battery-backed clock and calendar. The stratum number
indicates the number of network hops separating a device from an
authoritative source. Without authentication, NTP can be abused (e.g.,
by forcing the server to return incorrect time, thereby interfering with
authentication mechanisms that rely on timestamps, or by
resource-consumption attacks). NTP services have historically been
exploited in Distributed Denial-of-Service (DDoS) amplification attacks,
in which a small query results in a significant response directed at a
victim via IP spoofing.

The evolution of NTP mirrors that of other critical management
protocols, with later versions incorporating stronger cryptographic
controls to enhance security. NTPv3 introduced **cryptographic
authentication** capabilities. This feature prevents attackers from
sending **malicious time updates** to NTP clients. In this version,
authentication must be configured to prevent time spoofing, which could
invalidate logs or disrupt time-sensitive protocols. NTPv4 is described
in RFC 5905. It builds on previous versions by introducing IPv6 support,
more precise clock-discipline algorithms, and a dynamic server-discovery
scheme. This version ensures modern networks have robust time
synchronisation across IPv4 and IPv6 domains.

**Routing Protocols**

Routing protocols are the mechanisms and languages used by routers to
communicate with one another and to share essential information about
network reachability. Their core function is to enable routers to
determine the optimal forwarding path to distant networks dynamically.
Without routing protocols, a router would have knowledge only of the
networks to which it is directly connected. These protocols are critical
components of a network device\'s control plane, managing traffic that
sustains the internal functionality of the infrastructure.

**Classification of Routing Protocols**

Routing protocols can be classified by their scope of operation. The
operational boundary is typically defined by the **Autonomous System
(AS)**, which represents a network under a single administrative
control. Based on this scope, there are two types of routing protocols:

**Interior Gateway Protocols (IGPs):** These protocols operate
exclusively *within* a single AS. Examples include RIP, OSPF, and EIGRP.

- **Routing Information Protocol (RIP)**: A distance-vector routing
  protocol in which routers exchange a full copy of their routing tables
  with their directly attached neighbouring routers. This advertisement
  process typically occurs periodically. It utilises **hop count** as
  the metric to determine the best path to a destination network. The
  router selects the path with the lowest hop count, where a hop
  represents a transit through another router. A critical limitation of
  RIP is that the maximum number of router hops allowed between two
  points is **15**. Any destination requiring 16 hops or more is
  considered unreachable or assigned an **infinite metric**. RIP is
  susceptible to Routing Information Forgery and Control-Plane Attacks.
  In Routing Information Forgery, an attacker injects false routing
  information into the network, thereby tampering with the integrity of
  the routing tables. The Control-Plane Attack exploits RIP to generate
  excessive traffic or create unstable routes that target the router\'s
  CPU, thereby causing a DoS.

- **Open Shortest Path First (OSPF)**: It operates on a link-state
  algorithm that fundamentally differs from distance-vector protocols in
  how it views and updates the network topology. OSPF routers
  dynamically build a comprehensive topological map of the network (or
  area) in which they operate. Instead of exchanging full routing tables
  periodically, OSPF routers exchange detailed information known as Link
  State Advertisements (LSAs). Compromising OSPF allows an attacker to
  inject false routing information, divert traffic, or cause DoS. By
  default, routing updates are often sent in the clear, making them
  highly susceptible to manipulation. To prevent unauthorised systems
  from injecting false routes, cryptographic authentication must be
  configured. The most significant risk associated with OSPF is the
  exploitation of its control plane to cause instability or resource
  exhaustion. An attacker can flood a router with OSPF routing
  management packets (which are highly prioritised by the operating
  system) to overwhelm the CPU, thereby disrupting network services
  (DoS).

- **Enhanced Interior Gateway Routing Protocol (EIGRP)**: It is often
  described as a **hybrid routing protocol** or an **advanced
  distance-vector protocol** because it integrates features typically
  associated with both distance-vector and link-state routing models. It
  maintains a comprehensive **topology database**, a characteristic
  shared with link-state protocols, while simultaneously using neighbour
  information to operate, a characteristic of distance-vector protocols.
  EIGRP may use cryptographic authentication to protect its updates,
  typically employing MD5 or HMAC-SHA-256 hashing. However, tools like
  John the Ripper can be used to capture and crack these authentication
  keys. In addition, attackers can inject forged routing updates to
  manipulate the network topology using specialised tools such as Coly,
  which supports capturing EIGRP broadcasts and injecting packets to
  manipulate the configuration. Last but not least, EIGRP traffic is
  often prioritised by the system using Quality of Service (QoS)
  features, which can result in a flood of EIGRP management packets
  consuming excessive CPU resources and disrupting infrastructure
  functionality.

**Exterior Gateway Protocols (EGPs):** These protocols operate *between*
different ASs. BGP is the only EGP protocol used on the Internet between
ISPs to route Internet traffic.

- **Border Gateway Protocol (BGP)** is a path-vector routing protocol
  that derives from its reliance on tracking the entire path of ASs
  traversed to reach a destination network, rather than relying solely
  on router hop counts. BGP uses the number of AS hops as its primary
  metric for route selection, identifying the entire path that must be
  transited to reach a destination network. BGP\'s path selection is
  complex and not solely based on AS hops. The security posture of BGP
  is a crucial area for penetration testers and security architects. BGP
  is used to connect enterprise networks to their Internet Service
  Providers (ISPs), thereby defining the external perimeter and
  dictating how traffic reaches an organisation. The primary security
  risk involves an attacker forging routing information (route injection
  or hijacking). This can misdirect large amounts of Internet traffic
  away from legitimate destinations. Attacks targeting BGP therefore
  compromise the stability of this critical plane, allowing an attacker
  to inject false routing information or induce a DoS condition.

**Address Resolution Protocol (ARP)**

ARP is a fundamental, unauthenticated protocol that dynamically maps an
IPv4 address (Layer 3) to its corresponding physical Media Access
Control (MAC) address (Layer 2) within the local subnet. ARP is used
exclusively for IPv4 networks over multi-access link-layer protocols,
such as Ethernet and Wi-Fi. ARP is susceptible to ARP Cache Poisoning,
also called ARP Spoofing. ARP is fundamentally stateless and lacks
cryptographic authentication. This core design flaw makes it trivial for
an attacker to conduct a **Man-in-the-Middle (MITM) attack** by sending
unsolicited ARP replies containing false MAC-to-IP address mappings to
legitimate hosts. The victim systems accept these poisoned entries into
their local ARP cache. Traffic intended for the legitimate gateway
(router) or peer is consequently redirected through the attacker's
system, thereby enabling passive credential sniffing or active data
modification. ARP poisoning attacks are constrained to the local
broadcast domain (e.g., a single VLAN or subnet).

How does the stateless design of ARP facilitate Man-in-the-Middle (MITM)
attacks? Focus Area: Note that ARP lacks cryptographic authentication
and is fundamentally stateless, meaning victims will accept unsolicited
replies. Attackers exploit this by sending forged MAC-to-IP mappings

**Dynamic Host Configuration Protocol (DHCP)**

DHCP is an application-layer client-server protocol (UDP ports 67/68)
used to assign network configuration parameters, including IP address,
subnet mask, default router, and DNS server addresses. DHCP is
vulnerable to DHCP Spoofing and DHCP Starvation.

- **DHCP Server Spoofing (Rogue DHCP Server):** DHCP messages lack
  native security mechanisms and are not authenticated. An attacker can
  operate a rogue DHCP server that responds more quickly than the
  legitimate server, thereby providing clients with attacker-defined
  parameters. The attacker typically spoofs the default gateway or DNS
  server IP address to their own system, enabling MITM and redirecting
  traffic.

- **DHCP Starvation:** An attacker floods the DHCP server with numerous
  DHCP client requests using spoofed MAC addresses, aiming to exhaust
  the available IP address pool (DoS condition). This attack is often
  executed before a spoofing attack to ensure the rogue server has no
  competition.

**Cisco Discovery Protocol (CDP)**

CDP is a Cisco proprietary Layer 2 protocol used by devices to broadcast
information about themselves (hostname, platform, software version,
Layer 3 interfaces, and configuration details) to directly connected
neighbours. CDP operates by broadcasting frames in cleartext, providing
a ready-made **reconnaissance vector**. An attacker running a sniffer
can capture CDP announcements, revealing the device model, operating
system version, and Layer 3 addressing details. This information is
invaluable for identifying **published vulnerabilities** associated with
a specific software version or hardware platform, thereby facilitating
targeted exploitation. In addition, CDP flooding attacks can be launched
against switches, leading to CPU exhaustion (DoS). CDP should be
**disabled** on all interfaces where it is not strictly necessary,
particularly end-user access ports, to prevent information leakage to
unprivileged users.

**Network Redundancy Protocols (HSRP, VRRP, and GLBP)**

Network redundancy protocols provide first-hop router redundancy,
sharing a virtual IP and MAC address across multiple physical routers.

**Hot Standby Router Protocol (HSRP)**

HSRP is a **Cisco proprietary protocol** designed to provide **first-hop
redundancy** at Layer 3, ensuring continuous network operation in the
event of a router failure. In a typical network design, client machines
rely on a single, statically configured default gateway IP address to
send traffic outside their local subnet. If the router serving as that
default gateway fails, all devices relying on it would lose off-subnet
connectivity. HSRP solves this single point of failure by managing a
group of routers that share a single **virtual IP address** and a
**virtual MAC address**.

- **Virtual Router Group:** Multiple physical routers (or multilayer
  switches) are configured to belong to an HSRP group.

- **Active and Standby Roles:** Within the group, one router assumes the
  **Active Router** role, and a second assumes the **Standby Router**
  role. The **Active Router** is the device that currently owns and
  services traffic destined for the shared virtual IP and MAC addresses.
  The **Standby Router** monitors the Active Router and is prepared to
  take over the active role should the current Active Router fail.

- **Traffic Flow:** Workstations are configured to use the **virtual IP
  address** as their default gateway. Under normal conditions, the
  Active Router forwards all packets sent to this virtual IP address.

- **Failover:** Routers continuously exchange **hello messages** within
  the group. If the Standby Router stops receiving hello messages from
  the Active Router, it concludes that the Active Router has failed and
  assumes responsibility for routing traffic, transitioning to the
  Active role. The default failover time is approximately 10 seconds,
  though timers can be adjusted to achieve a failover time as short as 1
  second.

While HSRP is a crucial feature for ensuring **availability**, its
configurations are a critical area for security review. Like other
routing and redundancy protocols, HSRP is vulnerable if cryptographic
authentication is not implemented rigorously. An attacker who
successfully impersonates the Active Router can manipulate the Layer 3
forwarding path, causing all traffic intended for the legitimate gateway
to be redirected through the attacker\'s machine for interception (MITM
attack).

**Virtual Router Redundancy Protocol (VRRP)**

**VRRP is a vital Layer 3 network protocol, recognised as an IETF open
standard, designed** to provide **first-hop redundancy** within a
network infrastructure. Its primary function is to eliminate the single
point of failure that occurs when client systems rely on a single router
as their default gateway, thereby ensuring continuous network operation
and maintaining high availability. VRRP operates by enabling multiple
routers to share a single logical entity, known as a **virtual router**.
This virtual router possesses a shared **virtual IP address** and
**virtual MAC address** that client devices use as their default
gateway.

- **Group Function:** Routers participating in VRRP form a redundancy
  group.

- **Master and Backup Roles:** Within this group, one router takes on
  the **Master** role (analogous to the Active Router in HSRP),
  processing all traffic directed to the virtual IP address. Other
  routers act as backups, prepared to assume the Master role immediately
  upon detecting a failure.

- **Communication:** VRRP participants announce their configuration and
  status by sending packets to local **multicast groups**. Specifically,
  VRRP packets are sent to the IPv4 multicast address 224.0.0.18.

Older or poorly configured VRRP deployments are vulnerable to **route
hijacking** if weak authentication (or none at all) is used. If VRRP
uses simple (cleartext) authentication, tools can easily capture the
credentials, allowing an attacker to impersonate the master router and
divert network traffic. VRRPv3, notably, **does not incorporate native
authentication** in its design, demanding external Layer 3 security
controls. Even if cryptographic authentication is used (e.g.,
HMAC-SHA-256), tools designed for penetration testing, such as John the
Ripper, can be leveraged to attempt to **crack the authentication
keys**, potentially enabling the attacker to forge management packets
and manipulate the routing topology. In addition, because VRRP operates
within the high-priority Control Plane of network devices, flooding the
device with VRRP management packets can consume CPU resources,
potentially leading to a **DoS** condition on Cisco switches, even if
the protocol isn\'t explicitly enabled.

**VLAN Security Issues**

As we discussed in Chapter 5, VLAN is important for segmentation in
Layer 2. However, it uses various protocols such as DTP and VTP to
configure port and manage VLAN databases in witches. These protocols
introduce multiple vulnerabilities that is targeted by insider
attackers. In this section, we will both protocols and their
vulnerabilities.

**Dynamic Trunking Protocol (DTP)**

**DTP** is a proprietary Cisco Layer 2 protocol designed to automate the
negotiation of a link\'s operational mode between two interconnected
switches. DTP facilitates the negotiation between two switch ports to
decide whether the link should function as a **trunk** (carrying traffic
for multiple VLANs) or an **access port** (carrying traffic for only one
VLAN).

  ---------------------------------------------------------------------------
  Mode              Description
  ----------------- ---------------------------------------------------------
  **Access**        Forces the port into a permanent non-trunking state.

  **Trunk**         Forces the port into a permanent trunking state and
                    attempts to negotiate the link into a trunk with the
                    neighbor.

  **Dynamic Auto**  The default state for many older Cisco switches. The port
                    will only become a trunk if the neighboring device
                    specifically requests it.

  **Dynamic         The port actively attempts to negotiate a trunk link with
  Desirable**       its neighbor.

  **Nonegotiate**   Disables DTP entirely. The port must be manually
                    configured as either a trunk or an access port.
  ---------------------------------------------------------------------------

In penetration testing, DTP is a critical topic because its default
configurations often present a significant security risk, enabling an
adversary to bypass VLAN segmentation. The primary security concern for
a penetration tester is the **Switch Spoofing** attack, which is a form
of **VLAN Hopping**. Since DTP is often enabled by default (usually in
\"Dynamic Auto\" or \"Dynamic Desirable\" mode), a switch port is
essentially \"waiting\" for a negotiation request. An attacker can
connect a system to a switch port and use software (such as **Yersinia**
or **dtpscan.sh**) to emulate a switch by sending forged DTP negotiation
frames. If the negotiation is successful, the switch establishes a
**trunk link** with the attacker\'s machine. The attacker then gains
visibility and access to **all VLANs** permitted on that trunk, allowing
for unauthorized data interception and lateral movement across
supposedly isolated network segments.

**VLAN Trunking Protocol (VTP)**

VTP is a **Cisco proprietary protocol** used within a switched network
to automate the management and synchronisation of Virtual LAN (VLAN)
information. VTP allows a network administrator to create, modify, or
delete a VLAN on a single switch, typically a VTP server, and have those
changes propagated automatically to all other participating switches
within the same **VTP domain**. VTP management information is
distributed across the network via **trunk connections**. VTP switches
can be configured in different modes, such Server, Client, and
Transparent Modes. In server mode, we can create, update, and delete
VLANs. In client mode, we can't change VLAN database; however, clients
can accept changes from VTP server. In **transparent mode**, which is
often required when configuring advanced features like Private VLANs
(PVLANs) to prevent the switch from processing or overwriting local VLAN
databases based on global VTP advertisements.

From a security assessment perspective, VTP presents specific challenges
regarding traffic control and segmentation integrity. A critical
technical detail for the penetration testers is that **Port Access
Control Lists (PACLs) cannot filter VTP traffic**. This occurs because
the protocol is redirected to the switch's Route Processor (RP) before
the ACL can take effect. An attacker can launch unauthorised VLAN
propagation and Double-Tagging attacks against VTP switches.

- **Unauthorised VLAN Propagation:** If a rogue switch or a compromised
  device can participate in the VTP domain, it could potentially inject
  or delete VLAN configurations, causing widespread network disruption
  or providing an avenue for traffic interception.

<!-- -->

- **Double-Tagging Attack:** This attack (which does not rely on DTP
  being enabled) involves embedding a second 802.1Q tag within a frame.
  If the outer tag matches the native VLAN of a trunk, the frame
  bypasses the switch\'s decapsulation process and reaches the intended
  target VLAN.

**Spanning Tree Protocol (STP)**

STP, defined by the IEEE 802.1D standard, is a fundamental Layer 2
protocol designed to maintain a loop-free network topology within
bridged or switched environments. It allows for physical redundancy by
strategically blocking redundant data paths to prevent frames from
circulating endlessly. STP operates by building a logical tree structure
that spans all switches in a broadcast domain or VLAN. It utilises
special frames called **Bridge Protocol Data Units (BPDUs)** to exchange
information and coordinate the topology. The first step of STP is the
election of a **Root Bridge**, which serves as the central reference
point for the spanning tree. The switch with the lowest **Bridge ID
(BID)**, a combination of a configurable priority value and the
device\'s MAC address, is elected. Once the root bridge is established,
each port on every switch is assigned a role (described in Table \<\>)
and a state to ensure only one active path exists between any two
points. Ports transition through specific states to prevent loops during
topology changes: **Blocking** (discarding data), **Listening**
(building the tree), **Learning** (building MAC tables), and
**Forwarding** (fully operational).

  ---------------------------------------------------------------------------
  Port Role          Description
  ------------------ --------------------------------------------------------
  **Root Port**      The port on a non-root bridge that provides the
                     least-cost path to the root bridge.

  **Designated       The port on a segment that provides the least-cost path
  Port**             to the root bridge; all ports on a root bridge are
                     designated ports.

  **Non-designated   A port that is placed in a **blocking state** to
  Port**             eliminate loops.
  ---------------------------------------------------------------------------

In an unhardened environment, STP is highly susceptible to manipulation
by an adversary with network access.

- **Root Bridge Attack:** An attacker can send spoofed BPDUs advertising
  a *superior* Bridge ID (e.g., a priority of 0). This forces a
  recalculation of the spanning tree, electing the attacker's machine as
  the new root bridge. Once elected as the root bridge, all traffic
  between switches may pass through the attacker's system, enabling a
  **Man-in-the-Middle (MITM)** attack for data interception or sniffing.

- **Broadcast Storms:** If STP fails due to a bad module or
  misconfiguration, Layer 2 loops can result in broadcast storms, where
  frames loop endlessly, consuming all available bandwidth and
  potentially causing a denial of service (DoS) for the entire segment.

🎯 **CPSA EXAM TIP 4**

What are the primary risks of leaving CDP and STP unhardened on access
ports? Focus Area: CDP is a Cisco proprietary protocol that broadcasts
device details (hostname, OS version, IP addresses) in cleartext,
serving as a valuable reconnaissance vector for attackers. Similarly,
STP can be exploited through a Root Bridge Attack, where an attacker
sends spoofed BPDUs with a superior Bridge ID to become the central
point of the network topology. This forces traffic to flow through the
attacker\'s machine, enabling MITM interception.

**Remote Authentication Dial-In User Service (RADIUS)**

RADIUS is a general-purpose, fully **open standard** protocol described
in RFC 2865 and RFC 2866. It is widely used for network access, such as
connecting via wireless access points, VPNs, and wired switches. It uses
**UDP** **1812** for Authentication/Authorisation and **1813** for
accounting. RADIUS **combines** authentication and authorisation into a
single exchange. Because RADIUS combines authentication and
authorisation into a single exchange, it reduces granularity in
administrative control. Also, it is considered less secure than TACACS+
because it **only encrypts the password** field in the packet; the rest
of the header remains in cleartext. Here are some common attacks against
RADUIS:

- **Eavesdropping and Information Leakage:** Because only the password
  is encrypted, an attacker with a sniffer (like Wireshark) can easily
  capture usernames and session attributes, aiding in further
  reconnaissance.

- **Shared Secret Brute-Forcing:** The security of the RADIUS exchange
  depends on a shared secret between the client and server. If this
  secret is weak, an attacker can capture the traffic and perform an
  offline brute-force attack to discover the key.

- **Replay Attacks:** Unless specific mitigation such as nonces or
  timestamps are implemented, the UDP-based exchange may be susceptible
  to replay by an adversary suitably positioned on the network.

**Terminal Access Controller Access-Control System Plus (TACACS+)**

TACACS+ is a **Cisco proprietary** protocol (though extensively
documented) and is a new protocol compared to its predecessors. It is
primarily designed for **administrative access** to network
infrastructure devices. Uses **TCP** (Connection-oriented), making it
more reliable for management sessions. It uses TCP **49** and
**separates** all three AAA functions (Authentication, Authorisation,
and Accounting) into distinct elements. Under normal operations, it
**encrypts the entire body** of the packet, providing superior security
for administrative communications. In addition, it supports
**command-by-command authorisation**, allowing administrators to
restrict exactly which CLI commands a specific user can execute.
[]{dir="rtl"}

- **Shared Secret Brute-Forcing:** Similar to RADIUS, TACACS+ relies on
  a shared secret key. An attacker can attempt to brute-force this
  secret to decrypt captured packets.

- **DoS Attack:** As a Control Plane protocol, a flood of malformed
  TACACS+ requests can exhaust the CPU resources of the target network
  device, potentially causing a system crash.

- **Insecure Default Credentials:** Many administrative interfaces that
  use TACACS+ may still be accessible via default vendor credentials if
  the AAA fallback is not properly secured.

🎯 **CPSA EXAM TIP 5**

How does TACACS+ provide superior security for administrative access
compared to RADIUS? Focus Area: Be prepared to explain that TACACS+ (TCP
port 49) is generally more secure for management because it encrypts the
entire packet body, whereas RADIUS only encrypts the password.
Furthermore, TACACS+ separates AAA functions (Authentication,
Authorisation, and Accounting), which allows administrators to implement
command-by-command authorisation to restrict exactly what a user can do
on the CLI. Note that both remain vulnerable to shared secret
brute-forcing if weak keys are employed.

**Voice over IP (VoIP)**

VoIP is a category of technology that digitises spoken voice into data
packets and transmits those packets across an IP network. This
architecture allows voice traffic to share the same physical and logical
medium as data and interactive video. Organisations typically adopt VoIP
to replace traditional Public Switched Telephone Network (PSTN) systems
to achieve significant cost savings, reduce infrastructure complexity,
and enable enhanced services such as integrated video conferencing and
presence indicators. []{dir="rtl"}A VoIP session relies on separate
protocols for signalling (establishing the connection) and media
transport (carrying the actual audio).

- **Session Initiation Protocol (SIP):** SIP is an application-layer
  signalling protocol used to set up, maintain, and tear down multimedia
  sessions. SIP is highly flexible and can be carried over various
  transport-layer protocols, including **UDP**, **TCP**, and **SCTP**.
  Standard SIP typically listens on **UDP/TCP port 5060** for
  unencrypted signaling, while **port 5061** is reserved for SIP over
  Transport Layer Security (SIPS). SIP works in conjunction with
  **Session Description Protocol (SDP)** to negotiate session
  parameters, such as the codecs to be used and the IP addresses/ports
  for the media stream. An alternative to SIP is **H.323**, a signalling
  protocol suite defined by the ITU that provides multimedia
  communications over a network.

- **Real-time Transport Protocol (RTP):** While SIP handles the
  handshake, RTP is the protocol responsible for the actual delivery of
  voice and interactive video payloads. RTP operates at the transport
  layer and must be carefully prioritised by network hardware to avoid
  quality degradation.

- **Media Gateway Control Protocol (MGCP):** A call control protocol
  specifically designed for communication between VoIP network elements.

To assess the security of a VoIP implementation, penetration testers
must understand the function of each VOIP infrastructure components:

- **IP Phone**: A handset with an integrated Ethernet connection that
  digitises, packetises, and transmits voice data.

- **Call Agent**: A central repository for the network\'s dial plan; it
  determines how to route a call based on the digits dialled.

- **Voice Gateway**: Acts as a translator between different telephony
  environments, such as interconnecting a VoIP network with the PSTN or
  a traditional PBX.

- **PBX**: A Private Branch Exchange is a privately owned telephone
  switch that can interface with VoIP via a gateway.

- **WLC**: A Wireless LAN Controller can be used to centrally manage the
  wireless access points that service mobile VoIP clients.

From penetration testing perspective, VoIP introduces specific
vulnerabilities that must be evaluated:

- **Eavesdropping**: If signaling and media (RTP) are not encrypted, an
  attacker can use a network sniffer to capture and reconstruct the
  audio of VoIP calls.

- **Denial of Service (DoS):** Flooding a device with malformed SIP
  packets or UDP traffic can consume CPU resources, leading to service
  outages.

- **Unauthenticated Access:** Many IP phones use the TFTP on port 69 to
  download configuration files upon booting. Since TFTP lacks
  authentication, an attacker can brute-force filenames to retrieve
  configurations that may contain sensitive credentials or internal path
  details.

- **Information Disclosure:** Verbose error messages or improperly
  configured status pages (like those found in JBoss or Apache) can leak
  session tokens, usernames, and internal paths. Similarly, in Cisco
  environments, CDP can disclose a handset's software version, hardware
  platform, and power consumption. While useful for management, this
  information aids in attacker reconnaissance.

- **Lack of proper Quality of Service (QoS) mechanisms:** Voice traffic
  is highly sensitive to latency (delay), jitter (uneven arrival), and
  packet drops. An assessor should verify that the network implements
  marking and queuing mechanisms to ensure voice traffic receives
  priority over less time-sensitive data.

- **Lack of VOIP Traffic Segmentation**: It is a security best practice
  to place voice traffic on a dedicated Voice VLAN. Lack of voice
  traffic segmentation can blast data network and enable unauthorised
  parties to easily sniff voice traffic.

**Chapter Summary**

This chapter evaluates the processes and protocols essential for
maintaining the integrity, confidentiality, and availability of network
devices, contrasting the vulnerabilities of in-band management with the
superior security provided by out-of-band (OOB) management. It
highlights the necessity of replacing legacy, insecure protocols such as
Telnet, HTTP, and SNMPv1/v2c, transmit credentials in cleartext, with
secure alternatives like SSH, HTTPS, and SNMPv3 that utilise
cryptographic controls. The material also details critical threats to
the network control plane, including routing information forgery in
protocols like RIP and OSPF, ARP poisoning, and VLAN hopping facilitated
by the Dynamic Trunking Protocol (DTP). Furthermore, it compares
administrative access protocols, identifying TACACS+ as a more reliable
and secure standard than RADIUS due to its full-packet encryption and
support for command-by-command authorisation. Finally, the chapter
addresses VoIP infrastructure, stressing the importance of traffic
segmentation and encryption to prevent eavesdropping and session
hijacking on unencrypted SIP and RTP streams.
